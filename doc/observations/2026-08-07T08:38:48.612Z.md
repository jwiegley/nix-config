## Problem

`7a71d520` introduced `assertEnvironmentOnlyCredentials()` and called it at three credential
ingestion points. `0b9d8b77` removes one of them while repairing the patch:

```diff
-@@ -187,6 +199,7 @@ export async function loadConfig(cliOverrides: Partial<Config> = {})
-   if (repoCassDir) {
-     const { config: repoConfigRaw } = await loadRepoConfig(repoCassDir);
-+    assertEnvironmentOnlyCredentials(repoConfigRaw);
```

Enumerating every surviving call site in the patch:

| line | call | enclosing hunk context |
|---|---|---|
| 20 | `assertEnvironmentOnlyCredentials(parsedRaw)` | `loadGlobalConfigEnsuringInit()` |
| 33 | *(function definition, not a call)* | — |
| 48 | `assertEnvironmentOnlyCredentials(globalConfigRaw, cliOverrides)` | — |

Global config and CLI overrides remain guarded. **Repo-level config does not.** The only
remaining `repoConfig`/`repoCassDir` occurrence in the patch is a hunk context header.

## Impact

CM ingests configuration from three sources. A repository-local CM config carrying an `apiKey`
field is now loaded and merged without rejection, while the identical field in the global config
or on the CLI is refused with an error naming the environment variable to use instead.

That is the weaker half of the boundary: a repo config is the source most likely to be shared,
checked into version control, or received from someone else. CLAUDE.md states credentials stay
environment-only and must never reach config or generated files; the patch was named for that
invariant and no longer enforces it on that path.

The `cm` check builds green (`rc=0`), so nothing signals the loss. The repair fixed the build
by deleting the guard rather than by correcting the hunk that failed to apply.

## Suggested Fix

Re-add the call with corrected context. If the hunk failed because upstream moved the
`loadRepoConfig` call site, re-anchor it there rather than dropping it. A more robust placement
is *inside* `loadRepoConfig` itself, next to its parse — mirroring how the global path guards
`parsedRaw` inside `loadGlobalConfigEnsuringInit` rather than at the caller. That survives
upstream moving the call site.

Whichever placement, add a regression assertion so a future patch repair cannot silently drop it
again — the same shape `c81d191b` used for the Prime managed-settings path.
